# WEAK_LABEL_PLAYBOOK.md — 弱ラベル / 導出ラベルコンペの戦い方

> 出典: **RSNA Knee Abnormality Detection 2026**（我々の実戦 + 上位解法 23 件の読み込み + 終了後の追試）。
> 他ドメインでも、**「正解ラベルが少数しかなく、残りは別形式のヒントから導出する」構造**なら同じ戦い方が効く。
> 例: 自由文レポート → ラベル / 録音全体のタグ → 区間ラベル / 粗い外部アノテーション → 競技ラベル。

---

## 0. このコンペは「弱ラベルコンペ」か? 🔍

次のどれかに当てはまるなら、**この playbook を最優先で読む**。

- [ ] test と同形式の正解ラベルが、train の **ごく一部**にしか無い
- [ ] 残りのデータには「別形式のヒント」（自由文・粗いタグ・外部データセット）しか無い
- [ ] ホストが「ヒントからラベルを導出してよい」と明示している
- [ ] 公開 Discussion で「ラベルの作り方」が主要な話題になっている

⚠ **判定を定性語で済ませない**。"small subset" が **1.3%** なのか 30% なのかで設計が別物になる。
`notna().sum()` で 1 分で分かることを、設計を書く前に測る（`docs/LESSONS_FROM_PAST_COMPS.md` §16）。

## 1. 最重要の事実 — ラベル品質はモデル改善を上回る 💥

RSNA 終了後、**モデル側（architecture / augmentation / optimizer / epoch 数）を一切変えず、
ラベルソースだけを 7 位の公開ラベルに差し替えて再学習**した。

| 構成 | Public | Private |
|---|---|---|
| ラベルだけ差し替えた**単体**モデル | **0.968** | **0.958** |
| 我々の最終提出（5 モデル平均 + 公開ベースラインとのブレンド） | 0.958 | 0.945 |
| 我々の own-only 5 モデル平均 | 0.953 | 0.941 |

> **アンサンブルも公開ベースラインとのブレンドも、ラベル品質の差を埋められなかった。**

上位陣の writeup も同じことを独立に言っている:

- 7 位: 「**ラベルの変更がモデルの変更より一貫して大きかった**」
- 13 位: hard 0/1 → soft grade への変換**単体**がコンペ全体で最大の label lever（Private +0.015）
- 6 位: 「上位は全員、画像を読む LLM ラベルを持っていた。我々は持っていなかった」と自ら反省
- 3 位: 36 モデル積んでも Private は 0.958-0.959 に収束（= モデル数では埋まらない）

### 🎯 投資配分の指針

**序盤から「ラベル生成」に人と金を割く。** backbone 探索は後回しでよい。
ラベル段階の改善は、**全ての後続モデルに効く**（= 乗算的）のに対し、
architecture の改善は**そのモデル 1 本にしか効かない**（= 加算的）。

## 2. ラベルの作り方 — 3 種の read を使い分ける 📖

7 位（solo・Private 0.957-0.958・外部データ不使用）の設計が最も参考になる。
**同じ LLM に 3 通りの読み方をさせ、finding ごとに採用する read を変えた**。

| read | 入力 | prompt の立て方 | 小標本正解での AUC |
|---|---|---|---|
| **Structured** | report + **key slices**（矢状 9 / 冠状 9 / 軸位 6 = 24 枚） | 共通プロトコルで属性を採点 → ラベル確率 | .935 |
| **Image-only** | 全スライス（**report を見せない**） | 同じプロトコルを**画像だけ**から適用 | .919 |
| **Verification** ⭐ | report + 画像 | **「この report は誤りを含みうる下書きである」と明示し、各所見を画像で検証させる** | **.947** |

### 効いた工夫

- ⭐ **Verification read が単体最良**。report を「正解」ではなく「**検証対象の下書き**」として扱う
  prompt の立て方そのものが効いている。
- 🔀 **finding 別に採用 read を変える**。verification は Synovitis / Effusion で**過検出**した
  （有病率が .24→.31、.37→.48 に跳ね上がる）ので、その 2 つだけ structured + image-only の blend に差し替え。
- 📏 **key slice**: マルチモーダル LLM に全スライスは渡せない。**面ごとに代表スライスを選んで渡す**。
  （⚠ 選定アルゴリズムは writeup 非開示。自分で設計する余地がある）
- 🚫 **「report が陽性と書いていれば確率 1」というルールを撤廃**したことを明確な改善点として
  挙げたチームがある（21 位）。**ホストの判定基準は「画像がその基準を満たすか」であって、
  report の文言ではない**。自分のラベル生成に同じ罠が無いか点検する。

## 3. ⚠ frontier model と open-weight VLM は別物 — 我々の失敗から

**「画像を読む LLM」を open-weight VLM で代用しようとして失敗した**（RSNA、32 arm 規模の検証）。

| 検証したモデル | image-only の AUC | MRI 固有の情報を使えているか |
|---|---|---|
| MedGemma-1.5-4B | 0.500（**定数出力**） | ❌ |
| Qwen3-VL-8B / 32B | 0.51〜0.53 | ❌ |
| Lingshu-32B（医療チューニング） | 0.55 | ❌ |
| MedMO-8B（医療チューニング） | 0.41 | ❌ |

判定に使った必要条件が秀逸なので**そのまま流用する価値がある**:

> 🔬 **RI vs RIperm テスト**: 「report + **正しい画像**」と「report + **別サンプルの画像**」を比較する。
> 差が出なければ、そのモデルは**画像を見ているふりをしているだけ**。
> RSNA では 5 モデル中 **0 本**しかこのテストを通らなかった。

- ⚠ **サイズを上げても（8B→32B）医療チューニングしても改善しなかった**。
  同一ベース・同一サイズの清浄な対では、**医療チューニングした方が悪化**した。
- ✅ ただし **report-only なら open-weight も健闘**する（MedGemma-27B-text が非 GPT 最高 AUC 0.866）。
  **読めるのは文章であって画像ではない**、と切り分けること。
- 💡 **正しい結論**: 「画像を読む LLM は無効」ではなく、
  **「frontier multimodal model（GPT / Claude / Gemini クラス）でなければ医用画像は読めない」**。
  上位チームは全員 frontier model を使っていた。**ここをケチると路線ごと間違った判定を下す**。

### 代替路線 — 画像専門家の確率を text で渡す

生ピクセルを VLM に見せるのが駄目でも、**画像モデルが出した確率を LLM に text で渡す**路線は機能した
（RSNA 内製検証で **MRI 固有情報の寄与 +0.0405**、較正も改善）。
frontier model の予算が無い場合の現実的な代替になる。

## 4. 系統バイアスの補正 — 低コストで確度が高い ⚖

**6 チーム以上が独立に同じ手法へ収束**した、再現性の高い技術。

### 何が起きているか

LLM が付けたラベルが、**病変の有無ではなく「その施設が report にその語を書く習慣」を学習してしまう**。
RSNA では、ある所見の LLM ラベルが **report 中の単語の有無と 92% / 6% で一致**していた。

### 対処

```text
学習時のみ:  BCE( y , sigmoid( f(x) + b[site] ) )
推論時:      b[site] を外す（f(x) だけ使う）
```

- site の代理変数は **scanner メーカー / 機種 / 磁場強度 / report の言語 / coil** などで作れる。
  **明示的な施設 ID が無くても構築できる**のがポイント。
- 効果報告は **+0.006〜0.007（private）**。実装コストに対して明らかに割がよい。
- 🏗 **post-hoc 補正より構造的な解決のほうが強い**という報告もある（22 位）。
  内外側の疑似相関を、**重み共有 + 反対側を見せない**という構造で遮断したら効いたが、
  post-hoc の補正は **−0.007 と悪化**した。

## 5. teacher / student（自己蒸留）🔁

ほぼ全上位チームが採用。**LLM ラベル単体では終わらせない**。

```text
最終学習ターゲット = α × LLM ラベル + (1-α) × 画像モデルの OOF 予測
```

- **α = 0.5 前後**が複数チームで採用されている（7 位・22 位とも 0.5:0.5）。
- 🪢 **元の LLM ラベルを必ず一部残す**。全部を自分の予測に置き換えると
  **self-confirmation**（自分の間違いを強化する）に陥る。外部アンカーとして残す。
- 🔄 **世代数は頭打ちする**。10 世代回したチームの報告では、**最初の 4 世代で +0.017、以降は横ばい**。
  2〜4 世代で止めて別の軸に投資するのが効率的。
- ⚔ **OOF teacher か in-sample teacher か**は論争がある。
  20 位は「OOF モデルは 1 fold 少ないデータで学習されており teacher として弱い」として
  **in-sample（全データ学習モデルの訓練データ上の予測）を採用**し、全 leg で改善したと報告。
  → **両方試す価値がある**。ただしリークの扱いが変わるので、評価の物差しを固定してから比べる（§7）。

## 6. 小標本の専門家ラベルの扱い 🥇

RSNA の「Gold58」（専門医合意ラベル 58 件 = 全体の 1.3%）に相当するもの。

### ❌ 選抜（selection）に使わない

複数チームが独立に「使ったら悪化した」と報告している:

- 16 位: gold に fit させた stacking / per-label weight で **0.935 → 0.874** に悪化
- 19 位: **「gold 最適化が最も gold スコアが高く、最も public が低い」**という逆転を定量的に実証
- 我々も同じ結論（`docs/VALIDATION_PITFALLS.md`）

### ✅ 使ってよい 3 つの用途

1. **ラベル版どうしの品質比較**（診断）。ラベルを改良するたびにここで測り、段階を記録する。
2. **学習への直接投入**。ただし上書きではなく「正解として固定し、loss weight を上げる」形。
3. **fine-tuning + 重み空間マージ**（20 位の WiSE-FT）。
   小標本だけで fine-tune し、`θ = α·θ_FT + (1-α)·θ_base` で元の重みと補間する。
   本人いわく**コンペ最大の単発レバー（private +0.004〜0.006）**。
   ⚠ **我々は未検証**。「selection に使わない」と「training に使わない」は別の話、という発見。

## 7. 検証の作法 — ラベルを変えると物差しも変わる 📐

⚠ **最重要の落とし穴**。ラベル生成を変える実験では、これを守らないと数字が無意味になる。

- ✅ **本命と対照の評価ラベルを共通の 1 つに固定する**。
  仕組みとして「評価ラベルだけを差し替える指定」（`eval_source` 等）を最初から用意しておく。
- 🚨 実例: ラベルを差し替えた arm が CV 0.99、対照が 0.92 という劇的な差を出したが、
  **評価の正解ラベル自体が arm ごとに違っていた**だけだった（改善ではない）。
- 🧭 中立な物差しが無い場合、公正なのは
  **(a) 小標本の真の正解での診断値 (b) LB の実測** の 2 つだけと割り切る。
- 📈 **ラベル版ごとの品質を表で追う**。上位チームは全員これをやっている
  （例: `.935 → .919 → .947 → .943 → .949 → .947 → .952` と段階を記録し、どの改変が効いたかを特定）。

## 8. コスト管理 💰

大口の LLM API 生成は**金が飛ぶ**。RSNA での実例をそのまま教訓にする。

- 📊 **見積りと実費は乖離する**: 見積り ¥27,442 → 実費 約 ¥39,500（**1.2 万円超過**）。
  着手前に実トークンで再見積りし、**明示的な承認を取る**。
- 🔁 **二重起動事故**: 同じ全件生成が二重に走り約 ¥950 を無駄にした。
  **「大口生成の owner はこの 1 箇所」と決め、他からは打たない**ルールを書いておく。
- 🔒 **生成物は immutable にする**（RSNA では mode 444 + sha256 記録）。
  高価な生成物を事故で上書きしない。**再生成に金がかかるものは read-only に固定する**。
- 📉 **全件でなく部分集合でよいか考える**。「report と画像が食い違うセルだけ」のように
  効く範囲を絞れれば、**課金が 1 桁下がる**可能性がある。

## 9. 🚀 開始チェックリスト

コンペ開始〜1 週目で埋めること（`docs/COMPETITION_START_CHECKLIST.md` と併読）。

- [ ] 正解ラベルの実数を数えた（定性語で判断していない）
- [ ] ホストが「ヒントからのラベル導出」を許可しているか公式見解を確認した
- [ ] ホストの**判定基準の原文**を手元に置いた（report の文言ではなく基準で判定させるため）
- [ ] frontier multimodal model を使えるか（予算 / レート制限 / 利用規約）を確認した
- [ ] 小標本の専門家ラベルを **「selection には使わない」と文書で宣言**した
- [ ] 評価ラベルを共通固定する仕組み（`eval_source` 相当）を実装した
- [ ] ラベル版ごとの品質を記録する表を作った
- [ ] 大口生成の owner と承認フローを決めた
- [ ] site 代理変数（scanner / 言語 / 機種）が作れるか確認した
- [ ] 公開されているラベル資産（他参加者の公開 dataset）の有無とライセンスを確認した

## 10. 📌 一行まとめ

> **弱ラベルコンペは「モデルを作るコンペ」ではなく「ラベルを作るコンペ」。**
> backbone を 1 本増やす前に、ラベルをもう 1 段良くできないかを考える。
